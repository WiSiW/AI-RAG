# RAG 评估建议

首版建议维护 30–50 条真实业务问题，覆盖：

- 单文档事实题
- 跨章节归纳题
- 跨文档比较题
- 表格/列表/代码块问题
- 无答案问题
- 多轮指代与追问
- 容易产生过时信息或冲突信息的问题

## 核心指标

| 指标 | 目标 |
| --- | --- |
| Recall@5 | 正确分块出现在前 5 的比例 |
| MRR | 正确分块排序质量 |
| Citation Precision | 引用来源确实支持陈述的比例 |
| Answer Faithfulness | 回答只包含参考资料事实的比例 |
| Abstention Accuracy | 无答案时正确拒答比例 |
| p95 First Token Latency | 首 token 延迟 |
| p95 Full Answer Latency | 完整回答延迟 |
| Ingestion Success Rate | 文档入库成功率 |

## 调参顺序

1. 先确认解析文本质量与分块边界。
2. 再比较 BM25、向量单路与混合检索。
3. 使用固定候选集调整 RRF 参数。
4. 评估 Rerank 分数分布，不要直接假定 `0.3` 阈值适用于所有模型。
5. 最后调整 Prompt、Top-K 与生成模型参数。

## 建议记录字段

- 问题
- 所属知识库
- 标准答案
- 必须命中的文档与章节
- 实际召回分块
- 回答
- 引用
- 是否拒答
- 延迟
- 人工评分

## 分块语义完整性评估

应用内提供独立的“分块评估”运行，建议与检索评测配合使用：

- 先检查 L2 源文本覆盖率、边界完整性和 512–1024 token 粒度，再比较检索 Recall/MRR。
- 对 L1 检查章节关键事实覆盖与摘要忠实性，对 L3 检查原子事实清晰度和父块可还原性。
- 首轮每篇文档按固定种子分层抽样，默认最多 200 个 chunk，可通过 `initial_chunk_limit` 调整为 100–200；其他 chunk 在队列页标为 `not_selected`，按需手动加入。
- 每个 chunk 对应一次 LLM 请求，任务默认并发 2 且可配置为 1–4。每完成一块就提交规则/LLM 结果和进度，页面按“当前批次/总批次”显示。
- 连续两个 LLM 请求失败会打开熔断器，取消其余在途请求，并把待处理块保留为规则降级结果；稍后可在页面重试单块或全部失败块。
- 暂停采用协作取消：停止调度新请求，中断在途请求并把 chunk 标为 `interrupted`，任务进入 `paused` 后才允许删除；继续操作会重新排队中断和未完成项。
- 首次运行按文档分层抽取最多 24 个 chunk 人工评分（每粒度优先 4 个），用于校准 LLM 评判。
- 观察 `partial` 运行：它表示 LLM 调用被降级或部分文档失败，规则结果仍有效，不应与完整运行直接等同。
- 历史运行详情展示评估范围与粒度、知识库、文档和评估模型；运行创建时会把名称写入 `config_snapshot`，实体后续重命名或删除不影响历史识别。
- 使用历史运行对比检查分块模式、大小、重叠或 Prompt 变化是否导致完整性退化。

## 分块大小与重叠窗口调优

应用内“分块调优”页把参数选择拆成两阶段，避免直接修改生产索引：

1. **快速筛选**：默认比较 `256/512/1024/1536 token × 0%/10%/20%/25%`，另加当前参数基线。只构建隔离的 L2 原文向量和 BM25，固定单跳、Top 10、关闭 Rerank。
2. **深度验证**：管理员从 Pareto 前沿选择最多 5 组候选，构建完整 L1/L2/L3、多表示、增强、QA 和 Rerank 索引，每个候选分层评估最多 30 个可回答问题。

### 固定评测集

- 每个知识库单独维护评测集，推荐 50–100 条真实问题；运行门槛为 20 条可回答问题。
- 问题覆盖 `detail/comparison/summary/reasoning/table/code/no_answer`。
- 可回答问题必须有标准答案和至少一条原文黄金证据；证据以最小原文片段保存，不绑定当前 `chunk_id`。
- 无答案问题不进入 Recall 分母，只用于后续拒答质量分析。

### 指标定义

| 指标 | 定义 |
| --- | --- |
| Recall@K | 前 K 个召回块覆盖的不重复黄金证据数 / 该题黄金证据总数 |
| AllEvidenceHit@K | 全部黄金证据都被前 K 个块覆盖的问题比例 |
| MRR@10 | 首个黄金证据排名倒数的平均值 |
| ContextEvidenceDensity@K | 命中黄金证据 token 数 / 前 K 个召回块 token 总数 |
| p50/p95 latency | 单题检索耗时，深度阶段包含 Rerank |
| Faithfulness | LLM 按 1–5 判定答案事实是否由召回上下文支持 |
| Completeness | LLM 按 1–5 判定答案对标准答案关键事实的覆盖程度 |
| CitedGoldChunkRatio | 被引用且包含黄金证据的 chunk / 全部被引用 chunk |

证据命中以空白归一化后的完整片段包含为准。多证据、多文档问题按证据数计算 Recall，不会因为多个召回块重复包含同一证据而重复得分。

### Pareto 与推荐

- 前沿同时考虑最大化 Recall@5、Recall@10、ContextEvidenceDensity，最小化 p95 延迟和索引 token 成本。
- 不计算单一综合分。推荐 Top 3 仅用于辅助，优先过滤 p95 不超过基线 1.5 倍且索引 token 不超过基线 2 倍的候选。
- 对相对基线的 Recall 差值计算确定性 bootstrap 95% 区间；小数据集下不要把微小差异视为稳定提升。
- 快速筛选只用于候选收缩，不直接应用参数。只有深度验证状态为 `completed` 的 trial 才能保存为知识库默认参数。

### 隔离与清理

- 每次 trial 使用 `eval-*` 临时 Milvus collection 和 Whoosh 目录，成功、失败和取消后均清理。
- 历史运行只保留指标、配置快照和 Top 10 命中快照，不长期保留临时向量。
- 保存默认参数不会重分块现有文档；页面中的“重建现有文档”必须再次确认，并显示排队/跳过数量。
