# 文档分析入库与召回详细链路

核心：新知识库默认走 `v2`；PostgreSQL 保存权威 chunk 正文，Milvus/Whoosh 只保存召回表示；召回由 6 条逻辑路由加权 RRF 融合，然后在 Rerank 后从 PostgreSQL 回填原文，Chat 再动态构造上下文窗口。

当前主链路：

```text
上传 API
  -> MinIO + PostgreSQL(Document/IngestionJob)
  -> Celery
  -> 下载原文件
  -> 解析 ParsedDocument
  -> 引用区剥离
  -> L2 分块
  -> L2 摘要/关键词增强
  -> L1 章节摘要 + L3 原子块
  -> context_prefix
  -> 每块 3 个 QA 对
  -> Embedding
  -> Milvus v2 表示行 + Whoosh v2
  -> Document.ready

Search/Chat
  -> 参数校验
  -> 可选查询改写
  -> 单跳/多跳判定
  -> 按 Embedding 模型只生成一次查询向量
  -> BM25 + 5 类向量路由
  -> 按 chunk_id 加权 RRF
  -> PostgreSQL 回填原文和元数据
  -> Rerank
  -> Chat 动态上下文窗口
  -> LLM 回答 + 引用
```

# 一、入库链路

## 1. 上传并登记文档

入口：

```http
POST /api/v1/knowledge-bases/{kb_id}/documents
Authorization: Bearer <admin token>
Content-Type: multipart/form-data
```

具体入参：

```text
kb_id:          path，知识库 ID
file:           PDF / DOCX / MD / MARKDOWN / EPUB
chunk_size:     optional，默认取 KB settings，默认 512
chunk_overlap:  optional，默认取 KB settings，默认 64
chunk_mode:     optional，默认取 KB settings，默认 structure
tags:           comma-separated string，默认空
```

校验规则：

- 扩展名必须是 `.pdf/.docx/.md/.markdown/.epub`
- 默认单文件最大 `2048 MB`
- `32 <= chunk_size <= 8192`
- `0 <= chunk_overlap < chunk_size`
- 知识库不能正在导出/导入等写锁定状态
- 文件名只保留 basename

执行：

1. 文件流式写入本地临时文件，同时统计大小。
2. 生成 MinIO object key：

```text
documents/<uuid_hex>/<safe_filename>
```

3. 创建 `Document`：

```json
{
  "id": "<uuid>",
  "kb_id": "<kb_id>",
  "filename": "manual.pdf",
  "object_key": "documents/<uuid_hex>/manual.pdf",
  "content_type": "application/pdf",
  "size_bytes": 123456,
  "status": "pending",
  "tags": ["tag1"],
  "metadata_json": {
    "upload_source": "browser"
  },
  "chunk_mode": "structure",
  "chunk_size": 512,
  "chunk_overlap": 64
}
```

4. 创建 `IngestionJob`：

```json
{
  "id": "<uuid>",
  "document_id": "<document_id>",
  "status": "pending",
  "attempts": 0,
  "result": {}
}
```

5. 立刻提交事务并返回 `UploadResponse`：

```json
{
  "document": {
    "id": "<document_id>",
    "kb_id": "<kb_id>",
    "filename": "manual.pdf",
    "status": "pending",
    "chunk_count": 0,
    "reference_count": 0,
    "chunk_mode": "structure",
    "chunk_size": 512,
    "chunk_overlap": 64
  },
  "job": {
    "id": "<job_id>",
    "document_id": "<document_id>",
    "status": "pending",
    "attempts": 0,
    "result": {}
  }
}
```

此时只是登记成功，不代表解析完成。

## 4. 从 MinIO 下载原文件并解析

入参：

```text
Document.object_key
Document.filename 后缀
```

出参：

```python
ParsedDocument(
    source,
    title,
    elements: list[ParsedElement],
    full_text,
    metadata,
    tables: list[ParsedTable],
    page_traces,
    pipeline_meta,
    references,
)
```

其中：

```python
ParsedElement(
    type,       # title/paragraph/table/header/footer...
    text,
    level,      # 标题层级
    metadata,   # page/bbox/font_size/ocr_engine...
    bbox,
    confidence,
    source,
)
```

非 PDF：

```python
parse_document(temp_path) -> ParsedDocument
```

按扩展名派发：

```text
.docx    -> DocxParser
.md      -> MarkdownParser
.markdown-> MarkdownParser
.epub    -> EPUBParser
.pdf     -> 通常走 PDFProcessingPipeline
```

### PDF 子链路

PDF 的 `PDFProcessingPipeline.process(file_path)` 做：

1. PyMuPDF 逐页读取原生文本块。
2. 按字号判断标题层级：
   - `>= 中位字号 * 1.35`：level 1
   - `>= 1.20`：level 2
   - `>= 1.08`：level 3
   - 否则正文
3. 评估原生文本质量；扫描页/图片主导页进入 OCR。
4. 可选布局分析、OCR 引擎链识别。
5. 表格抽取，生成 `ParsedTable`，保留：
   - 表格 ID
   - 页码
   - bbox
   - 表头、单元格、行、Markdown
   - 抽取引擎、质量分
6. 表格与正文元素去重叠后重新按阅读顺序合并。
7. 表格默认生成不超过 180 字的说明，模型失败则规则回退。
8. 输出 `ParsedDocument` 和工作流指标：

```json
{
  "status": "ready 或 degraded",
  "pages_total": 20,
  "native_pages": 17,
  "ocr_pages": 3,
  "failed_pages": [],
  "ocr_engine_counts": {"paddle": 3},
  "layout_sources": {"geometry": 20},
  "tables": 4,
  "warnings": [],
  "ocr_dpi": 300
}
```

## 7. 生成 L2 分块

调用：

```python
split_document(
    parsed,
    mode=chunk_mode,
    chunk_size=document.chunk_size,
    chunk_overlap=document.chunk_overlap,
    embed_fn=lambda texts: gateway.embed_texts(profile, texts),
    semantic_threshold=0.72,
)
```

支持模式：

```text
structure / recursive / fixed / paragraph / sentence / semantic / parent_child
```

出参：

```python
list[ChunkData(
    content,
    section_path,
    token_count,
    chunk_index,
    metadata,
)]
```

Token 计数不是 tiktoken，而是确定性规则：

```text
每个中文字符         = 1 token
连续英文/数字标识符  = 1 token
其他非空白字符       = 1 token
```

分块行为：

- `structure`：按标题层级形成章节路径，再按元素聚合。
- PDF 的 `structure` 优先走 `LayoutAwareChunker`，表格作为原子块处理。
- `recursive`：段落 -> 句子 -> 超长 token 窗口。
- `fixed`：严格 token 滑窗。
- `paragraph/sentence`：按对应单位聚合。
- `semantic`：对相邻句子向量计算余弦相似度，低于阈值切分；Embedding 失败时自动回退句子聚合。
- `parent_child`：生成父块信息并写入 child metadata，但当前标准 L1/L2/L3 链路仍以 L2 为主。
- 超长元素使用 `chunk_size - chunk_overlap` 作为步长滑窗。

章节路径示例：

```text
第 3 章 部署 > 3.2 配置 > 3.2.1 数据库
```

实现位置：`D:\wsw\AI-RAG\backend\app\chunking\modes.py`

## 9. L2 摘要和关键词增强

调用：

```python
enricher.enrich(
    enrichment_profile,
    [(row.id, row.content) for row in chunk_rows],
)
```

入参：

```text
profile: ENRICHMENT 或 LLM 模型，可为空
chunks: list[(chunk_id, raw_content)]
batch_size: 默认 8
```

Prompt 输出结构：

```json
[
  {
    "chunk_id": "<原样返回>",
    "summary": "约 50 字，最多 80 字",
    "keywords": ["5-10 个 BM25 友好关键词"]
  }
]
```

清洗规则：

- 摘要最多 80 字。
- 关键词最多 10 个，单关键词最多 24 字。
- 停用词、空词、重复词过滤。
- 模型返回少于 5 个关键词时，用 jieba 规则补足。
- 模型调用失败、JSON 非法或缺失 chunk 时整批规则回退：

```json
{
  "summary": "规则截取摘要",
  "keywords": ["规则词"],
  "hypothetical_questions": [],
  "status": "degraded",
  "meta": {
    "generated_by": "rules",
    "fallback_reason": "invalid_model_output",
    "prompt_version": "chunk-enrichment-v2"
  }
}
```

写入 L2：

```text
summary
keywords
enrichment_status
enrichment_meta
```

表格 chunk 的摘要优先使用表格描述：

```text
row.summary = table.description or enrichment.summary
```

## 12. 为每个 L1/L2/L3 生成 3 个 QA 对

输入 `QASource`：

```python
QASource(
    chunk_id,
    content,
    contextual_text,
    section_path,
    keywords,
    summary,
    granularity_level,
)
```

批次默认 4。

Prompt 要求：

```text
detail
comparison
summary
```

每个 chunk 每类 1 个，回答最多 300 字，答案只依据当前 chunk。

清洗和重试：

1. 第一次批量生成。
2. 检查是否缺少类型。
3. 对缺类型 chunk 做定向重试。
4. 仍缺失则规则补齐。
5. 最终严格排序为 `detail/comparison/summary`，最多 3 个。

输出写入：

```json
{
  "qa_pairs": [
    {
      "question": "安装前需要关闭什么？",
      "answer": "安装前必须关闭电源。",
      "question_type": "detail"
    },
    {
      "question": "电源状态与安装流程有什么关系？",
      "answer": "...",
      "question_type": "comparison"
    },
    {
      "question": "安装准备工作的核心要求是什么？",
      "answer": "...",
      "question_type": "summary"
    }
  ],
  "hypothetical_questions": [
    "安装前需要关闭什么？",
    "电源状态与安装流程有什么关系？",
    "安装准备工作的核心要求是什么？"
  ],
  "enrichment_meta": {
    "qa_generated_by": "model",
    "qa_prompt_version": "qa-generation-v1",
    "qa_count": 3,
    "qa_types": ["detail", "comparison", "summary"],
    "qa_degraded_reasons": []
  }
}
```

重要语义：

- `qa_pairs` 是权威结构。
- `hypothetical_questions` 只是题目投影。
- **QA 答案不生成向量、不进 BM25、不进 Rerank、不进最终上下文。**
- 只有问题文本会作为 `question` 表示写入 Milvus。

## 13. 生成原始向量和多表示向量

### 原始向量

只对 L2 的上下文文本生成：

```python
text = contextual_text = context_prefix + "\n" + content
original_vectors = _embed_texts(profile, texts)
```

入参：

```text
ModelProfile
texts: list[str]
```

出参：

```text
list[list[float]]
```

Embedding 网关行为：

- 每批默认 32 条。
- 输出向量做 L2 归一化。
- 校验返回数量和配置维度。
- 原始 L2 Embedding 失败会直接导致文档入库失败。

### 多表示

| 粒度 | Milvus 表示 |
|---|---|
| L1 | `l1_summary` + 3 个 `question` |
| L2 | `original` + `summary` + 3 个 `question` |
| L3 | `l3_atomic` + 3 个 `question` |

具体索引文本：

```text
l1_summary -> context_prefix + "\n" + L1 content
original   -> context_prefix + "\n" + L2 content
summary    -> L2 summary 原文
question   -> QA 问题原文
l3_atomic  -> context_prefix + "\n" + L3 content
```

额外表示 Embedding 分 batch 调用：

- 单批失败时，只把相关 chunk 标记为 `degraded`。
- 不阻止已经成功的 `original` 向量。
- 记录 `degraded_reasons=["representation_embedding_failed"]`。
- 记录 `representation_count`、`question_count`、`qa_count`。

```text

```

Embedding 已经归一化，因此内积检索等价于余弦相似度检索。

### Whoosh v2

```text

```

字段：

```text
chunk_id
doc_id
source
section
content
keywords
```

## 3. 单跳/多跳判定

函数：

```python

```

入参：


特征：


2. 规则分数 `>= 0.75`：多跳。

5. BERT 不确定或不可用，调用轻量 LLM 只回答“是/否”。
6. 最终 fallback：
   - `rule_score >= 0.4` 或 `bert_probability >= 0.5`：多跳。

## 6. 加权 RRF 融合

实际 Chat/Search 使用：

```python
weighted_rrf_fuse(...)
```

每个知识库每条路由形成独立的 ranked list：

```text
bm25
l1
original
summary
questions
l3
```

默认权重：

```text
bm25       1.0
l1         0.8
original   1.0
summary    1.0
questions  1.0
l3         0.6
```

如果 KB 设置了 `fusion_weight`，最终路由权重为：

```text
route_weight = fusion_weight * retrieval_weight[route]
```

计算公式：

```text
RRF(chunk) = Σ route_weight / (60 + rank_in_route)
```

特点：

- 按 `chunk_id` 去重。
- 同一 chunk 被多个路由命中时分数累加。
- 保留：

```text
matched_representations
representation_scores
representation_ranks
matched_questions
vector_score
vector_rank
bm25_score
bm25_rank
```

RRF 输出：

```json
{
  "chunk_id": "c1",
  "rrf_score": 0.04127,
  "metadata": {
    "matched_representations": ["bm25", "original", "summary", "questions"],
    "representation_scores": {
      "bm25": 12.34,
      "original": 0.85,
      "summary": 0.82,
      "questions": 0.79
    },
    "representation_ranks": {
      "bm25": 2,
      "original": 3,
      "summary": 5,
      "questions": 8
    },
    "matched_questions": ["安装前需要关闭什么？"]
  }
}
```

候选数量：

```text
max(rag_global_candidate_top_k=60,
    final_limit * knowledge_base_count)
```

默认通常为 60。

## 8. Rerank

调用：

```python
reranker.rerank(
    profile,
    query,
    chunks,
    top_k,
    threshold=0.3,
)
```

用于重排的文本不是 `context_text`，而是：

```text
context_prefix + "\n" + DB 原始 content
```

如果存在 `context_prefix`，会加在前面。

网关请求：

```json
{
  "model": "<rerank model>",
  "query": "用户问题",
  "documents": [
    "[文档: ... / 章节: ...]\n原始 chunk 正文",
    "..."
  ],
  "top_n": 16
}
```

默认批处理：

```text
每批最多 16 个文档
每批约 800 tokens
```

超长文档会被切成片段，同一文档取最高分。

输出：

```text
chunk.rerank_score = round(score, 6)
```

排序和过滤：

1. 按 rerank score 降序。
2. 只保留 `score >= threshold`。
3. 截断到 `top_k`。

阈值：

- 单 KB：`kb.settings.rerank_threshold`，默认 `0.3`
- 多 KB：`rag_multi_kb_rerank_threshold`，默认 `0.3`

如果没有可用 rerank profile：

- 不报错。
- 直接按 RRF 顺序截断到 `top_k`。
- `rerank_score` 仍为 `null`。

## 9. Chat 的动态上下文窗口

只有 Chat 设置：

```python
expand_context=True
```

Search 不展开。

对每个命中 chunk：

### 9.1 基础片段

```text
[context_prefix]

[命中片段]
<DocumentChunk.content>
```

### 9.2 父上下文

- L3：取 `parent_chunk_id` 对应 L2 的 content。
- L2：
  - 若 metadata 有旧 `parent_content`，使用它。
  - 否则取同文档、同 `section_path` 的所有 L2 拼接。
- 以命中 chunk 原文作为锚点，前后各截取 320 tokens。
- 去掉锚点自身，避免重复。
- 追加：

```text
[父文档局部上下文]
...
```

### 9.3 表格上下文

- 表格总预算默认 1000 tokens。
- 表格 ID 来自当前 chunk 或其父 chunk。
- 全局去重。
- 放得下：注入完整 Markdown。
- 放不下：注入表格描述。
- 已包含在当前 chunk 中：标记 `existing_chunk`，不重复注入。

### 9.4 前后邻块

- 同文档。
- 同 granularity level。
- 按 `chunk_index` 找前一块和后一块。
- 前块取尾部 180 tokens。
- 后块取头部 180 tokens。
- 如果邻块已经包含在父窗口中，则跳过。
- 若追加后超过单 chunk 上下文预算 1200 tokens，则不追加。

### 9.5 输出

```python
chunk.context_text
```

并在 metadata 写入：

```text
context_parent_included
context_parent_source
context_previous_included
context_next_included
context_tokens
context_tables
```

### 9.6 总上下文预算

Chat 最后执行：

```text
所有命中 chunk 的 context_text 总 token <= 6000
```

按最终排序依次选取；超预算的后续 chunk 跳过。

# 三、当前实现中值得注意的两个一致性问题

## 1. 问题向量路由的 representation type 不一致，按当前代码会导致 questions 路由没有命中

入库时 `_build_representations()` 写入的是单数：

```python
extra_items.append((row, "question", question_index, str(question)))
```

即 Milvus 中：

```text
representation_type = "question"
```

但召回时 `HybridRetriever.retrieve_routes()` 查询的是复数：

```python
("questions", "questions")
```

最终 Milvus 过滤条件变成：

```text
representation_type == "questions"
```

而实际写入值是：

```text
representation_type == "question"
```

因此按当前入库代码产生的数据，`questions` 向量路由会查不到问题向量。测试里的 FakeVector 没有模拟 Milvus 的过滤语义，所以当前测试没有暴露这个问题。

相关位置：

```text
D:\wsw\AI-RAG\backend\app\services\ingestion_service.py:667
D:\wsw\AI-RAG\backend\app\retrieval\hybrid_retriever.py:153-158
```

## 2. `kb.settings.final_top_k` 当前没有参与实际 top_k 计算

知识库默认设置中有：

```json
{
  "final_top_k": 5
}
```

但当前检索最终数量实际来自：

- `/search` 请求的 `top_k`，默认 `5`。
- Chat 没有 `top_k` 字段，使用全局 `rag_final_top_k=5` 或 `rag_multi_kb_final_top_k=6`。

也就是说，修改 KB 的 `final_top_k` 目前不会改变 Chat 的实际结果数。

相关位置：

```text

D:\wsw\AI-RAG\backend\app\services\chat_service.py:423-427
```
